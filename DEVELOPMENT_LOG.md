## 2026-08-13 (сесія 2) — Git, запуск гри, баг центрування канвасу

**Контекст:** користувач ініціалізував git-репозиторій самостійно (перевірив
`node_modules/` вже був у `.gitignore` і коректно ігнорується —
`git check-ignore` підтвердив правило спрацьовує, тож нічого міняти не
довелось). Далі попросив запустити гру й, побачивши скріншот, повідомив, що
канвас зміщений вправо і обрізається знизу.

**Діагностика:** відтворив баг headless Chrome-скріншотами
(`chrome --headless=new --screenshot`) на кількох розмірах вікна, потім
підтвердив кореневу причину інжектнутим debug-скриптом, що виводив
`getBoundingClientRect`/`getComputedStyle` контейнера й канвасу прямо в DOM
(тимчасова правка `index.html`, прибрана одразу після діагностики).

Корінь проблеми: `src/main.js` мав `autoCenter: Phaser.Scale.CENTER_BOTH`,
а `#game-container` в `style.css` — власне `display:flex;
align-items:center; justify-content:center`. Обидва механізми одночасно
намагались центрувати той самий канвас: Phaser's `ScaleManager.updateCenter()`
додає `margin-left`/`margin-top` до канвасу так, ніби він у звичайному
block-потоці (тобто позиція рахується від лівого/верхнього краю
контейнера) — але канвас УЖЕ був відцентрований flexbox'ом, тож margin
Phaser додавався ПОВЕРХ вже відцентрованої позиції, зсуваючи канвас далі
вправо. По вертикалі зсув не завжди проявлявся однаково — оскільки гра
портретна (896×1152), а вікно зазвичай landscape, `Scale.FIT` вже
використовує 100% доступної висоти (без запасу для центрування), тому
видимий ефект — канвас впритул до верху/низу вікна, що виглядало як
"обрізання", хоча пікселі не губились.

**Виправлено:**
- `src/main.js`: `autoCenter` → `Phaser.Scale.NO_CENTER` (центрування
  лишили тільки за CSS flexbox, прибрали конфлікт двох механізмів).
- Додано обгортку `#game-frame` всередині `#game-container`
  (`index.html`, `src/style.css`, `parent: 'game-frame'` в `main.js`) —
  Phaser рахує розмір канвасу відносно `#game-frame`, а не
  `#game-container`, і `#game-frame` навмисно на 24px менший за
  контейнер (`calc(100% - 24px)`), щоб гарантувати видимий відступ з усіх
  боків навіть тоді, коли `Scale.FIT` вперся б в один із вимірів
  контейнера впритул. Просте `padding` на `#game-container` тут не
  спрацювало б: Phaser рахує розмір батька через
  `getBoundingClientRect()`, який включає padding в бордер-бокс, тож
  Phaser все одно спробував би заповнити повний контейнер.
- Перевірено на трьох співвідношеннях вікна (1920×1080, 900×1400,
  1200×900) headless-скріншотами — центрування коректне і відступи
  видимі з усіх боків на кожному.

**Рішення:** не робити висновок "щось не так з Phaser" і не переписувати
логіку сцени — це був суто CSS/config конфлікт у двох рядках, вирішений
без зачіпання ігрової логіки (відповідає принципу "порт, а не
переписування" з `CLAUDE.md`).

## 2026-08-13 (сесія 3) — Деплой на GitHub Pages, додаткова стійкість до обрізання

**Контекст:** користувач попросив інструкцію публікації демо на
`esiteq.github.io/pacman-phaser/`, а потім — створити workflow і
закомітити/запушити. Після цього, підтвердивши, що все працює (скріншот
показав коректне центрування), попросив додатково гарантувати, що гра
"ніколи" не обрізається.

**Зроблено:**
- Створено `.github/workflows/deploy.yml` — стандартний GitHub Actions
  workflow (`actions/checkout` → `npm ci` → `npm run build` →
  `actions/upload-pages-artifact` → `actions/deploy-pages`), запускається
  на кожен push у `main`.
- Створено `DEPLOYMENT.md` з детальною інструкцією (GitHub Actions +
  альтернатива через пакет `gh-pages`, таблиця типових проблем).
- Закомічено й запушено (`git commit` + `git push origin main`).
- При наступному `git pull` виявлено, що на remote з'явився ще один
  commit від GitHub — `.github/workflows/jekyll-gh-pages.yml`,
  автоматично згенерований GitHub при увімкненні Pages через веб-UI
  (Settings → Pages → Source → GitHub Actions інколи підставляє
  Jekyll-шаблон за замовчуванням, якщо не розпізнає стек). Обидва
  workflow мали `concurrency: group: "pages"` і незалежно намагались
  задеплоїти в один і той самий Pages-простір — Jekyll-workflow білдив
  би сирий репозиторій (README.md як Jekyll-сайт) замість `dist/` з
  Vite-збіркою гри, тож після кожного push демо могло непередбачувано
  показувати то гру, то Jekyll-сторінку, залежно від того, який job
  фінішував останнім. Видалено `jekyll-gh-pages.yml` — лишився тільки
  наш `deploy.yml`.
- На прохання "нічого не обрізалося ніколи" додатково зачищено
  `src/style.css`:
  - Прибрано дублюючі `width: 100%; height: 100%;` на `#game-container`
    (він і так `position: fixed; inset: 0`, що вже достатньо для
    fixed-елемента — зайва percentage-based висота лише додає ще один
    механізм розрахунку розміру, який теоретично міг розійтись з
    `inset` на нетипових мобільних браузерах).
  - Додано `@supports (height: 100dvh) { html, body { height: 100dvh } }`
    — `100%`/`100vh` на iOS Safari рахується відносно "великого" viewport
    (коли адресний рядок прихований), через що контент може виїжджати
    під панель браузера після її появи назад; `100dvh` відстежує
    актуальний видимий viewport. Це прогресивне покращення (старі
    браузери просто ігнорують `@supports`-блок і лишаються на
    попередній поведінці).
  - Перевірено headless-скріншотами на 1920×1080 і 375×667 (типовий
    мобільний розмір) — центрування й відступи не зламались.

**Рішення:** видалення Jekyll-workflow — це не те, про що просив
користувач буквально, але прямо стосується надійності самого демо
(без цього наступний push міг непередбачувано показати не гру), тому
виправлено проактивно й описано в CHANGELOG, а не мовчки.

## 2026-08-13 (сесія 4) — Накладання HUD-тексту й нема стартової мелодії на живому демо

**Контекст:** користувач перевірив живий деплой на
`esiteq.github.io/pacman-phaser/` і повідомив дві проблеми: (1) стартова
мелодія не програється, (2) "все одно обрізається". Скріншот був
826×941 (вузьке портретне вікно).

**Діагностика:**
- Спершу перевірив, чи демо взагалі показує актуальну збірку (побоювання
  через Jekyll-конфлікт з попередньої сесії): `curl -sI` показав
  `last-modified` за кілька хвилин до звернення, `curl -s` підтвердив у
  HTML посилання на `#game-frame` — тобто це вже наш актуальний білд,
  Jekyll не заважає.
- Відтворив headless-скріншотом живого демо (`chrome --headless
  --window-size=827,941 https://esiteq.github.io/pacman-phaser/`) — і
  побачив причину "обрізання": це не втрата пікселів, а **накладання
  тексту**. HTML-заголовок `.header-buttons .title` ("PAC-MAN", `position:
  fixed; left:0`) перекривав власний HUD гри ("1UP", намальований
  Phaser'ом усередині canvas) в один і той же рядок ~y=20-45px, даючи
  нечитабельне "PAC-MAN1P". Це відбувається тільки коли в канвасу мало
  лівого відступу — тобто на вузьких/портретних вікнах, де ширина, а не
  висота, є "зв'язуючим" виміром для `Scale.FIT` (на широких landscape
  вікнах лівого чорного поля вистачало, щоб заголовок і HUD не
  перетинались — тому цей баг не проявлявся в попередніх перевірках на
  1920×1080). Користувач, вочевидь, і сприйняв цей текстовий "стик" як
  "обрізання".
- Для звуку: `SoundManager.play('game_start')` викликається одразу в
  `GameScene.create()` → `newGame()` → `startGameplay(true)`, тобто до
  будь-якого жесту користувача. `HTMLMediaElement.play()` без
  попереднього user gesture блокується політикою автовідтворення
  браузера (Chrome: залежить від Media Engagement Index сайту — свіжий
  домен на кшталт щойно відкритого `esiteq.github.io` майже завжди
  блокує; `localhost`, відвідуваний багато разів під час розробки, міг
  випадково "проскакувати" через накопичений engagement, тому баг не
  впадав в очі раніше). Помилка гасилась мовчки через
  `.catch(() => {})` в оригінальному коді.

**Виправлено:**
- `index.html` / `src/style.css`: прибрано `<span class="title">PAC-MAN
  </span>` і мертве правило `.header-buttons .title` — це був суто
  декоративний елемент (гра й так показує "1UP"/"HIGH SCORE" через
  власний HUD), не частина порту оригінальної гри. `justify-content`
  шапки змінено з `space-between` на `flex-end`, щоб кнопки
  паузи/звуку лишились притиснутими праворуч (з одним елементом
  `space-between` кинув би їх ліворуч).
- `src/utils/SoundManager.js`: `play()` тепер запам'ятовує
  (`this.blockedSound`) звук, якщо `Audio.play()` відхилено браузером;
  `unlock()` (вже викликається по першому `keydown`/`pointerdown` для
  розблокування `AudioContext`) повторно намагається програти цей
  звук. Тобто стартова мелодія тепер прозвучить одразу, як тільки
  гравець вперше натисне клавішу чи торкнеться екрана — замість того,
  щоб мовчки пропасти назавжди.
- Перевірено headless-скріншотами живого коду на 827×941 і 1920×1080 —
  "1UP"/"HIGH SCORE" більше не перетинаються з нічим.

**Рішення:** видалити заголовок, а не намагатись "розсунути" його від
HUD через додатковий відступ у `#game-frame` (наприклад, збільшивши
верхній padding) — той підхід не дає гарантії на довільних
співвідношеннях сторін (позиція canvas завжди залежить від
центрування, а header — від фіксованих координат viewport, тобто вони
в принципі не пов'язані одне з одним математично). Прибрати джерело
конфлікту простіше й надійніше, ніж намагатись його заздалегідь
"обрахувати" для всіх розмірів екрана.

## 2026-08-13 (сесія 5) — Стартова мелодія не грає на 2-му рівні й далі

**Контекст:** користувач повідомив, що мелодія `game_start` звучить
тільки на самому початку гри, а на другому рівні й далі — ні. Уточнив
бажану поведінку: після втрати життя мелодія НЕ має повторюватись (і
зараз коректно не повторюється), а от на старті КОЖНОГО рівня — має.

**Діагностика:** `GameScene.startGameplay(initialStart)` грає
`game_start` лише коли `initialStart` truthy, і використовує той самий
прапорець для тривалості показу "READY!" (4500мс на самому початку гри,
2000мс у решті випадків). Виклики:
- `newGame()` → `startGameplay(true)` — початок гри, мелодія грає. ОК.
- `deathSequence()` → `startGameplay()` (без аргументу) — після втрати
  життя, мелодія коректно НЕ грає. ОК, як і хотів користувач.
- `advanceLevel()` → `startGameplay()` (без аргументу) — старт нового
  рівня. Тут і був баг: мелодія не грала, бо `initialStart` не
  передавався.

**Виправлено:** `startGameplay(initialStart, playMelody = initialStart)`
— розділив прапорець "це прямо найперший старт гри" (впливає лише на
тривалість "READY!") від прапорця "грати мелодію" (незалежний другий
параметр). `advanceLevel()` тепер викликає `startGameplay(false, true)`
— мелодія грає, а тривалість "READY!" лишається короткою (2000мс), як і
була на переходах між рівнями раніше. `deathSequence()` не займали —
досі викликає `startGameplay()` без аргументів, тому й далі без мелодії
й з короткою тривалістю.

**Рішення:** не просто передати `startGameplay(true)` в `advanceLevel()`
— це заразом розтягнуло б "READY!" до 4500мс на кожному новому рівні
(побічний ефект, про який не просили і який змінив би темп гри).
Розв'язав прапорці незалежними параметрами замість одного
перевантаженого `initialStart`.

  користувач попросив зупинитись.

**Гіпотези, які лишились неперевіреними** (для майбутньої сесії, якщо
користувач повернеться до цього):
- Масштабування екрана Windows (125%/150% DPI) або зум браузера — може
  впливати на заокруглення `calc(100% - 24px)` чи на те, як
  `getBoundingClientRect` округлюється при нецілому `devicePixelRatio`.
- Інший браузер, не Chrome (Edge/Firefox) — інша поведінка `100dvh`,
  `position:fixed;inset:0`, чи заокруглення flex-розмірів.
- Можливо, скріншот користувача робиться інструментом, який кадрує НЕ
  весь viewport, а щось трохи менше (наприклад, вікно програми
  скріншотів залишає позаду смужку) — це б виглядало точнісінько як
  "обрізання", хоча сторінка рендериться коректно. Це не вдалось
  перевірити чи спростувати без прямого доступу до екрана користувача.

## 2026-08-13 (сесія 7) — Шапка (GitHub/кнопки) не вирівняна з лабіринтом

**Контекст:** після додавання посилання "GitHub" користувач показав
скріншот широкого вікна, де шапка (GitHub + кнопки паузи/звуку) сидить
у кутку самого вікна браузера, а не лабіринту — оскільки `.header-
buttons` розтягнута на всю ширину viewport (`left:0; right:0`) і
прибита до `top:0`, тоді як canvas (лабіринт) на широких вікнах
центрується з великими чорними полями по боках (леттербоксинг). Тобто
шапка й лабіринт мали різні "системи координат": одна — весь viewport,
інша — фактичний прямокутник canvas, розмір і позиція якого залежить
від Phaser Scale.FIT і невідомі наперед у CSS.

**Виправлено:** у `main.js` додано `syncHeaderToCanvas(game)` —
читає `game.canvas.getBoundingClientRect()` і виставляє шапці inline
`left`/`top`/`width`/`height`, де `height` = висота верхньої
HUD-смуги гри (`TOP_UI_ROWS`, вже імпортований з `mazeData.js`),
переведена у поточний масштаб екрана (`rect.height / height`).
Викликається один раз після `Phaser.Core.Events.READY` (щоб canvas
уже мав фінальний розмір) і повторно на кожен
`Phaser.Scale.Events.RESIZE` (свій internal resize-event
ScaleManager'а, а не голий `window.resize` — надійніше, бо саме
Phaser вирішує, коли canvas дійсно перерахувався). В CSS `.header-
buttons` прибрано `top/left/right:0`, лишився тільки
`position:fixed` (координати тепер ставить JS) і `align-items:center`
всередині виставленої JS-висоти вертикально центрує вміст шапки.

**Перевірено:** headless-скріншоти на 1920×1080 (landscape,
леттербоксинг по боках), 827×941 і 900×1400 (portrait, леттербоксинг
зверху/знизу) — у кожному шапка тепер рівно по ширині з лабіринтом і
вертикально по центру HUD-рядка "1UP"/"HIGH SCORE", а не в кутку вікна.

**Рішення:** не намагався розв'язати це чистим CSS (наприклад,
`aspect-ratio` на обгортці навколо canvas, що імітувала б розмір
canvas) — canvas-у розмір і так рахує Phaser під капотом, і дублювати
цю логіку в CSS означало б два джерела правди, які можуть розійтись.
Синхронізація через реальний `getBoundingClientRect()` canvas-а і
власну подію ScaleManager'а — єдине джерело правди, без дублювання.
